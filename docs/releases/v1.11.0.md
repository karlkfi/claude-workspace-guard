Minor release: a skill you wrote yourself is now as quiet as one you installed from someone else. You install your own by symlinking the repo it lives in. File arguments are compared after `realpath`, so those files landed outside `~/.claude/skills/` and its read exemption never reached them.

> [!IMPORTANT]
> **A `~/.claude/skills/` entry that symlinks out now carries the read exemption to its target.** Launching your own skill's scripts — `python3 ~/workspace/skills/foo/lint.py` — stops prompting. Reads only: a write into the target repo still prompts, and a cross-checkout write keeps its deny. If you worked around this with a `WORKSPACE_GUARD_READ_ALLOW_PREFIXES` entry naming the repo your skills live in, this release makes it redundant.

The target must hold a `SKILL.md`, which is what stops the directory becoming a laundering slot: `ln` is not a guarded command, so without that test `ln -s /etc ~/.claude/skills/x` would exempt `/etc` for reads. Resolution goes one level deep and runs per invocation, so the exempt set is exactly the skills installed right now. Uninstalling one drops its exemption with no stale state, a symlink deeper inside a skill's tree widens nothing, and a sibling directory in the same repo that nobody installed stays outside. See [Allowed read prefixes](https://github.com/karlkfi/claude-workspace-guard/blob/v1.11.0/README.md#allowed-read-prefixes) for the full exemption list.
